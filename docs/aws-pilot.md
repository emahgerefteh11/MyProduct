# AWS billing pilot: operator preflight and release checks

## Start with the existing export, not a new one

1. Confirm the approved AWS account and one existing export. Use an authorized operator session, not public GitHub Pages. Check the export type, format, compression, delivery versioning, last delivery and bucket Region. The direct adapter currently supports **Legacy CUR, CSV, GZIP, keep new report versions**. CUR 2.0 CSV can be evaluated separately by manual mapping; it is not proof of direct connector support. Do not change an export to make it fit.
2. Pick one finalized billing period if available. Verify finalization inside the operator session; record the fact, not invoice IDs. The dates in a file can cover the full period before the invoice is final. If only an open period is available, label the comparison provisional.
3. Confirm the expected bucket owner, Region, existing manifest key for that period, and encryption requirements. Prefer the Region shown in the export destination or S3 console. If needed, an operator can use the Region header from [HeadBucket](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadBucket.html) for discovery; a Region header on a denied request is not evidence of read access. Verify access with a signed [GetObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html) for the exact manifest in the confirmed Region, with the expected bucket owner. Do not grant bucket listing just to disambiguate a 403. If the manifest or data parts use SSE-KMS, verify signed reads of the manifest and a representative listed part for each known key or Bucket Key configuration with the intended assumed role. A manifest success does not prove data-part decrypt access. AWS uses the [object ARN or bucket ARN as the encryption context](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingKMSEncryption.html#encryption-context), depending on Bucket Key status. Keep S3 access limited to the approved export; verify the existing [cross-account KMS authorization](https://docs.aws.amazon.com/kms/latest/developerguide/key-policy-modifying-external-accounts.html) separately if the role and key live in different accounts. With no listing, a wrong or missing key can also look denied.
4. Check the manifest’s assembly ID, period and part list. Confirm the exact cost column (`lineItem/UnblendedCost` for the current Legacy connector), currency and exact-case ownership header in populated parts. Same label is not the same cost basis; do not substitute the net-unblended discount column. Both paths must use the exact same assembly. The local adapter limits are 10 CSV parts, 20 MiB compressed and expanded, 100,000 rows and 500 columns. Matching header-only parts are allowed in the connector and counted for revision integrity; omit them from the manual selection and record why. Missing, corrupt or incompatible parts fail, as do assemblies with no populated rows.

Keep export locations, billing rows, account identifiers, authentication details and private reports in the approved environment. Do not paste secrets or billing files into chat, put them in GitHub or store them in public web assets. Record eligibility and failures using only the data the operator is approved to share.

## Connect and prove the release checks after approval

- The private host and workload identity are a separate approval gate. Scope its customer role to the chosen export and required permissions. Use a tenant-specific external ID with the configured trust relationship; never supply credentials from a browser or job payload. Check role assumption separately from S3 object access. Fetch a temporary session at job execution, not when queued; AWS [limits chained role sessions to one hour](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html). Treat explicit expiry as retryable with a fresh session, not as “manifest missing.” Preserve the last valid report and timestamp on the failed attempt. Reopen only a still-current, authorized scope on retry.
- Exercise the private, authenticated flow with one tenant and a second isolated tenant. Compare upload and connected report totals, signed credits, service buckets, ownership and unallocated spend for the same time range and currency. Record file and revision evidence only in the approved environment. An exact replay must not change the accepted result or timestamp. Safely exercise a revised assembly, a failed refresh, and revoked access under separate approved conditions; do not manufacture a revision by modifying a real AWS export. Confirm unauthorized tenants cannot see reports or jobs, and the customer-facing flow works after the approved deployment.
- Record fixture, CI, live export and deployed flow evidence separately. A successful manifest read is preflight, not a completed pilot. Do not mark the MVP complete on synthetic evidence alone.

## Rehearse recovery on the approved host with sample data

Before storing pilot data, restore to an isolated destination and check that the accepted report and its job outcome match the same snapshot. Verify that a completed job replay does not make a new object request. For a single-host SQLite option, use a consistent [SQLite backup](https://www.sqlite.org/backup.html), not a raw copy of a live database file that could omit its write-ahead log. [SQLite WAL](https://www.sqlite.org/wal.html) requires processes sharing the database to run on the same host. A test backup is not a hosting choice or a guarantee that post-backup writes survive.

Keep restored workers and private reads disabled until the operator verifies current tenant access, connection grants and revocations, and reconciles pending jobs against what happened after the backup. Never auto-run queued jobs from a restored snapshot. Test recovery and data retention on the selected private host before allowing real billing data.

## Private host readiness gate (synthetic data only)

No hosting option is selected. First ask whether there is an approved existing host, identity provider and operator. Record the candidate, owner, access boundary, available resources, incremental cost estimate and rollback path. Request approval before provisioning, granting AWS or pilot access, or enabling any live route.

- **Durable storage.** A dedicated single-host process with an encrypted retained local block volume is one candidate to evaluate, not a production recommendation. If using EC2, verify the data volume's [retention on instance termination](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/preserving-volumes-on-termination.html) rather than assuming a root volume persists. For a replaceable or multi-replica service, evaluate a separately approved durable transactional store instead of assuming the task's disk is durable. AWS [deletes ECS service-managed task EBS when a task terminates](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/configure-ebs-volume.html#ebs-volume-termination). Do not move SQLite WAL onto a network filesystem. The hosted store must publish the accepted revision and terminal job result together and fence the write against the current tenant, mapping and connection generation.
- **Identity and serving.** Serve private data only over verified HTTPS on the approved origin, with current server-verified session and tenant grants. No-store for private replies. Test manager, viewer, foreign tenant, and revoked session through the actual ingress and routes. Test same-origin intent checks on writes; prove access revocation and disconnect do not permit an old job to publish or a cached overview to grant access. Verify the workload can use only its scoped temporary role and exact configured export objects; the preflight checks above still apply.
- **Replacement drill.** Publish a synthetic $105 revision, with its timestamp and terminal job, then replace the workload instance rather than merely closing and reopening a connection. Verify the same revision, totals, timestamp and job on the replacement, no replay fetch, no stale grant, and no automatically resumed queue from a restore. Also restore a consistent backup to an isolated target with reads/workers disabled until reconciliation. Verify what survives abrupt termination versus restoration from an older backup and record measured recovery time, maximum missing work, and the operator who can roll back.
- **Resource envelope.** Use one-product and high-cardinality product variants at 25,000 synthetic rows plus a concurrently running refresh. Record encoded overview/detail bytes after gateway framing, cold and warm response latency, snapshot read/parse cost and peak memory, queue bounds, timeouts and storage growth. The loopback overview projection measured roughly 1.1–1.2 KB, but the fixture still reads/parses the full accepted snapshot and is not a host benchmark. If the approved candidate cannot serve these under its agreed resource and spend limits, stop and propose a change; do not quietly widen the limits.

A synthetic pass is permission to present the evidence, not to promote. Record commit, candidate, what passed or failed, rollback evidence, blockers and next approval. Only an approved live export and the deployed customer checks can close the pilot.

## Local synthetic resource baseline

Run `node scripts/benchmark_private_billing.cjs` with Node.js 22 or later and SQLite support on a development machine with sufficient free memory (allow at least 1 GiB). It generates two synthetic reports, then reads each 20 times from temporary SQLite using the real private overview adapter, in fresh processes with batches of one or four requests. It uses no AWS, network service, or customer data. It measures body bytes, read/parse time and process peak RSS; requests call the adapter directly, not through HTTP. The synchronous query and parse steps share one event loop, even in a four-request batch.

Two Linux/Node 24 runs returned a 1,427-byte overview for the 28.5 MB distinct-product snapshot. The four-request case observed about 780–805 MiB process peak RSS and 1.16–1.39 s local p95. These are development-machine observations, not host capacity or release limits. The small response does not remove the full snapshot read/parse. Before approving a host, compare a bounded stored overview published atomically with the accepted revision and measure the remaining detail-read cost. Repeat with a concurrent refresh, TLS and gateway on the approved host.
